# ZiYan Agent 游戏设计方案（统一实施版）

更新时间：2026-08-16

## 0. 文档定位与当前边界

本文是 ZiYan 的 Agent 游戏模块唯一设计真值源。它描述的是一个低 CPU、低内存、可验证、可回滚的纯手机端游戏流程 Agent，不是通用大模型游戏机器人。

当前项目优先级：ZiYan 核心兼容与发布门禁优先于 Agent。Agent 的正式实现必须在核心包完成稳定发布验收后开始；在此之前只允许实现不影响核心热路径的 UI、数据结构、离线解析和模拟测试。

本文中的“自动运行”仅指用户已学习、已验证、且游戏规则允许的重复流程。未知游戏、账号安全、支付、验证码、隐私数据、不可逆操作和规则不确定情况，必须暂停并交给用户。

## 1. 产品目标

用户使用 ZiYan 的流程：

```text
选择游戏
→ 人工学习：用户正常操作，Agent 记录可验证流程
→ 演练：Agent 只识别和解释，不触控
→ 小范围回放：执行低风险已学习流程
→ 自动运行：按状态机、规则和预算完成重复任务
→ 异常时安全暂停、保存现场、等待用户处理
```

正式目标：

1. 让用户把已知游戏流程转成稳定 Lua 状态机；
2. 让 Agent 在游戏更新、屏幕差异、掉线、死亡、维护、弹窗等情况下不乱点；
3. 在 iPhone 7/7 Plus/8/8 Plus、iOS 13–16 rootful/rootless 的既有 ZiYan 架构内运行；
4. 不引入第二个帧守护、不把常规视觉/触控退回 HTTP、不同步逐帧截图；
5. 让每次动作、异常、同步和规则升级都有证据、版本和回滚点。

非目标：

```text
未学习新游戏的通用理解
开放世界自由策略或复杂实时竞技决策
常驻大模型、Ollama、iOS-MCP、云 API、收费推理服务
账号注册、验证码处理、规避游戏风控
自动私聊、批量社交、提取联系方式或外部营销
自动支付、充值、交易、出售、分解、强化或丢弃高价值物品
```

## 2. 不可违背的运行纪律

1. 复用唯一 `ziyan_framecap`，始终保持 `FC_N=1`；
2. 常规识别保持现有 find/getColor/keep 的内嵌热路径；
3. 不新增竞争性守护进程，不杀 SpringBoard/backboardd，不通过重启系统掩盖问题；
4. Agent 与业务脚本绝对互斥；
5. 音量“-”只控制业务脚本，音量“+”只控制 Agent；
6. 同时按两个音量键时丢弃事件，300ms 去抖，停止优先；
7. 不确定即停止触控；未知状态、账号验证、付费确认、隐私页面一律人工接管；
8. rootful/rootless 一律走现有路径解析，禁止在业务规则中写死单一路径；
9. 不读取短信、验证码、密码、支付信息、私聊或敏感通知；
10. 所有运行、学习、同步和恢复均可被用户停止，并在停止后释放会话资源。

## 3. 用户入口、权限与状态

### 3.1 页面入口

ZiYan 首页保留：

```text
[我的脚本]：导入、选择、运行 Lua/Python 业务脚本
,：选择游戏、人工学习、演练、自动运行、查看现场
```

Agent 游戏页面：

```text
当前游戏：<自动识别/用户选择>
模式：[人工学习] [演练] [自动运行]
状态：<未运行/学习中/演练中/运行中/等待人工/安全停止>
操作：[开始] [暂停] [继续] [停止并清理] [查看现场] [规则版本]
```

### 3.2 音量键

```text
音量“-”：业务脚本开始/暂停/恢复/停止；不得启动或停止 Agent。
音量“+”：Agent 未运行时打开游戏列表或开始当前模式；学习中结束学习；
           演练/自动运行中立即停止 Agent。
```

音量“+”停止优先级最高。停止动作不依赖网络、OCR、同步或模型结果。

### 3.3 全局状态机

```text
IDLE
├─ 选择人工学习 → MANUAL_LEARN
├─ 选择演练       → DRY_RUN
├─ 选择自动运行   → AUTO_RUN
└─ 音量+          → GAME_LIST / 当前默认模式

MANUAL_LEARN
├─ 暂停           → LEARN_PAUSED
├─ 音量+ / 完成   → LEARN_REVIEW
├─ 放弃           → STOPPED_SAFE
└─ 异常           → PAUSED_NEEDS_HELP

DRY_RUN
├─ 验证通过       → READY_TO_RUN
├─ 未知/冲突      → PAUSED_NEEDS_HELP
└─ 音量+          → STOPPED_SAFE

AUTO_RUN
├─ 状态成功       → AUTO_RUN
├─ 无进展/异常    → RECOVERY / PAUSED_NEEDS_HELP
├─ 完成目标       → STOPPED_SAFE
└─ 音量+          → STOPPED_SAFE

任何状态
└─ 前台 Bundle 改变、账号/支付/验证码、用户停止 → 立即停止触控
```

`PAUSED_NEEDS_HELP` 不得伪装为“运行中”。界面必须显示暂停原因、所在步骤、已尝试次数和可执行操作。

## 4. 统一架构

```text
现有 ziyan_framecap（唯一帧源）
→ FrameObserver（新帧、前台、方向、frame_seq）
→ Vision（找色优先，找图按需，OCR 最少化）
→ StateRecognizer（状态与置信度）
→ Policy / Planner（目标、候选、预算、风险）
→ ActionExecutor（白名单动作、取消令牌、幂等控制）
→ Verifier（前后条件、资源变化、前台验证）
→ Recovery（有限恢复或暂停）
→ EventLog / Evidence（轻量、可回放、可清理）
```

模块职责：

| 模块 | 只负责 | 不负责 |
|---|---|---|
| FrameObserver | 帧、前台、方向、时间、序号 | 业务决策 |
| Vision | 输出视觉特征与置信度 | 直接点击 |
| StateRecognizer | 将特征映射为游戏状态 | 选择高层目标 |
| Planner | 在已学习候选中选择下一目标 | 直接调用坐标 |
| ActionExecutor | 执行一个受限动作 | 推断业务结果 |
| Verifier | 判断动作是否达到预期 | 盲目重试 |
| Recovery | 处理已分类异常 | 无限制自救 |
| LearningRecorder | 记录人工证据和草稿 | 自动发布未验证规则 |
| SyncManager | 同步已验证制品 | 远程控制另一台手机 |

正常自动运行不得启动 Python、HTTP 服务、MCP、Ollama 或大型模型。Python 仅可作为用户显式启动的隔离业务脚本能力，不能进入 Agent 热路径。

## 5. 统一数据模型

所有运行时数据使用同一层次，避免规则、设备差异和学习草稿混杂。

```text
GameProfile（游戏逻辑层）
├─ identity：bundle_id、display_name、游戏版本特征
├─ goals：经验/材料/金币/日常/安全等用户目标
├─ states：状态定义、视觉条件、超时、允许动作
├─ activities：日常、Boss、地图、背包等活动卡片
├─ policy：预算、优先级、重试、人工确认
└─ version：hash、来源、验证证据、回滚点

DeviceOverlay（设备校正层）
├─ device_profile：逻辑尺寸、像素尺寸、方向、安全区
├─ anchors：锚点、ROI、模板缩放变体
├─ transforms：相对坐标映射
└─ validation：本机成功/失败证据

SessionState（短期运行层）
├─ belief_state：角色、资源、地图、网络、风险、置信度
├─ active_goal / active_activity / current_state
├─ budgets / retry_count / cooldowns
├─ cancellation_token
└─ event_ring：最近有限事件
```

### 5.1 强制字段

任何状态、动作、活动和规则必须可追溯：

```text
id、名称、来源、适用 bundle_id、版本、创建时间
前置条件、动作、后置验证、超时、最大重试
成本、可逆性、幂等性、风险级别
置信度、最近成功次数、失败次数、最后验证时间
```

### 5.2 动作合同

动作必须是声明式白名单，不能允许任意代码在运行时扩张：

```text
action_type：tap / swipe / wait / open_known_panel / stop
target：anchor + normalized_point + ROI
precondition：必须命中的状态与前台 Bundle
postcondition：预期状态/颜色/图像/OCR/资源变化
timeout：等待窗口
max_retry：默认 0 或 1
idempotent：是否可安全重复
cost：体力、金币、门票、药品或 none
user_confirmation：never / first_use / every_time
```

没有前后验证的动作只能作为人工学习草稿，不能进入自动运行。

## 6. 视觉、坐标与跨屏幕校正

### 6.1 识别优先级

```text
找色 / 固定角标
→ 相对区域内找图
→ 必要时 OCR 关键词
→ 多特征置信度融合
→ UNKNOWN
```

OCR 只用于文字确实必要的状态；数字、多行或超时的 OCR 结果不得作为单一高风险决策依据。

### 6.2 跨设备规则

禁止直接复制绝对像素坐标。学习结果必须保存：

```text
logical_point、normalized_point、ROI、anchor、tap_offset、方向、安全区、前后验证
```

目标设备执行时：

```text
读取本机 DeviceOverlay
→ 在相对 ROI 寻找多个锚点
→ 计算映射
→ 执行低风险动作
→ 验证后更新本机校正层
```

8 Plus 与 iPhone 7 的学习可以双向共享“状态语义、动作合同、验证条件”，但不共享绝对坐标。每台设备只更新自己的 overlay。

### 6.3 校正失败

锚点不足、误差过大、方向不符、游戏界面变更时：

```text
CALIBRATION_FAILED / PROFILE_OUTDATED
→ 停止触控
→ 保存最小现场
→ 提示在本设备人工学习或确认
→ 不污染其他设备的通用规则
```

## 7. 人工学习

### 7.1 学习前检查

```text
确认非业务脚本运行中
确认 front_bid 是目标游戏
读取游戏版本特征、方向、尺寸和安全区
清理旧会话临时缓冲
观察稳定画面 3–5 秒
```

启动动画、加载页、通知遮挡和账号页面不得被直接编译为业务状态。

### 7.2 记录内容

每次用户操作记录：

```text
动作类型与逻辑位置
动作前状态、关键帧索引、锚点、front_bid、frame_seq
用户可选意图：进入/确认/领取/攻击/返回/等待等
动作后状态、等待时间、资源变化、成功/失败
异常分支与用户处理方式
```

敏感页面（密码、验证码、支付、私聊、系统权限）不截图、不 OCR、不写原文，只写 `MANUAL_REQUIRED`。

### 7.3 低干扰交互

不应每次点击都询问。仅在以下情况提示用户补充：

```text
同一位置存在多个可能按钮
动作后没有稳定变化
无法判定意图
进入敏感页面
前台/版本发生变化
检测到不可逆或高成本动作
```

用户可暂停、继续、撤销最近一步、删除异常片段、标记成功/失败、命名关键状态、设置等待时间。

### 7.4 分支学习

学习器必须保存成功与失败分支：

```text
正常路径
弹窗路径
资源不足路径
死亡/回城路径
网络/维护路径
仓库已满路径
未知页面路径
```

未验证分支只能作为人工专用备注，不能自动执行。

### 7.5 质量门禁

学习结束生成质量报告：

```text
状态数、可验证动作比例、未确认步骤、锚点稳定性
重复状态合并数、异常分支覆盖、风险动作数、可回放次数
```

只有满足以下条件才可进入 staging：

1. 每个自动动作都有前置和后置验证；
2. 没有敏感数据和未声明的高风险动作；
3. 至少一次 DRY_RUN 可完整识别；
4. 本机至少一次低风险真机回放成功；
5. 规则、设备 overlay、Lua 模块各自有版本和 hash。

## 8. 编译、演练、发布与回滚

```text
人工学习会话
→ draft state_graph
→ 静态检查（路径、动作合同、风险、敏感页）
→ DRY_RUN
→ 单机低风险回放
→ staging
→ 灰度发布
→ 正式规则
```

发布规则：

1. 新规则先在产生它的设备上验证；
2. 同一设备连续成功 3 次，或两台不同设备各成功 1 次，才能成为共享候选；
3. 失败率异常、游戏版本变化、锚点失效时降级到上一稳定版本；
4. 正在运行的会话保持当前版本，停止后再切换；
5. 任何规则都可从版本列表回滚，不得静默覆盖。

Lua 是手机端主执行形式。生成器只能输出预设安全模板：状态识别、动作、验证、超时、最大重试、未知暂停；不得生成任意 shell、网络服务或自修改逻辑。

## 9. 自我决策

### 9.1 四层决策

```text
目标层：安全挂机 / 日常 / 经验 / 材料 / 金币
策略层：选活动、选地图、回城、换图、等待、人工接管
战术层：入口、目标选择、战斗流程、领奖、退出
动作层：找色/找图/OCR → 一个触控动作 → 验证
```

高层仅在状态变化、目标完成、资源变化、死亡、维护、网络异常或周期点重算；低层只执行当前已验证步骤。

### 9.2 belief_state

Agent 只根据有来源、置信度与 TTL 的信息决策：

```text
等级、战力、生命/法力、金币、体力、门票、药品、背包空间
当前地图、活动开放状态、冷却、每日次数、队伍状态
网络状态、敌对风险、前台 Bundle、当前状态
```

任何关键字段为 `UNKNOWN`，则相应高风险候选不可执行。

### 9.3 候选评分

先硬门禁，后排序：

```text
硬门禁：已学习、前置满足、开放、资源足够、预算允许、风险可接受
评分：预期收益 - 时间成本 - 资源成本 - 失败风险 + 历史成功权重
```

用户设置目标优先级，例如：

```text
安全 > 日常完成 > 经验 > 材料 > 金币
```

不以收益为由自动充值、购买门票、复活或消耗高级道具。

### 9.4 预测—执行—验证

```text
预测一个动作的结果
→ 确认前置条件
→ 执行最小动作
→ 等待新帧/回执
→ 验证预期画面、资源与前台
→ 成功：更新 belief_state
→ 失败：有限恢复、重新规划或暂停
```

同一动作没有新帧、成功回执或状态变化时，不得重复发送。购买、复活、强化、交易、邮寄、分解、丢弃等非幂等动作默认人工确认。

### 9.5 有限探索

未知页面不做自由探索。允许的探索仅为一次低风险观察或人工学习候选采集；出现成本、账号风险、未知弹窗或无结果时立即停止。

## 10. 活动、地图与 Boss

### 10.1 活动卡片

每个日常、Boss、攻沙或副本使用独立 `ActivityProfile`：

```text
activity_id、名称、入口锚点、开放时间
等级/战力/前置条件、体力/金币/门票成本、次数与冷却
进入、战斗、结算、退出状态图
完成条件、失败条件、回城条件、最大时长与最大动作数
```

未人工学习和验证过的地图不自动进入。

### 10.2 角色条件与资源预算

地图选择前重新读取等级、战力、金币、体力、门票、药品和活动状态。用户可设置：

```text
最大体力、金币、门票、药品、挑战次数、单局时长
禁止自动复活、购买、使用稀有道具
活动优先级、避让规则、允许的地图集合
```

达到预算、条件不够、维护、次数耗尽或读取不确定时跳过，不反复点击入口。

### 10.3 Boss 失败与被玩家击杀

```text
Boss 失败/超时/药品不足 → 标记 BOSS_TOO_HARD，默认不连刷，重新调度
玩家击杀/明确回城      → 立刻停止攻击和移动，不追击、不反击
                         → 原地图进入避让冷却 → 重新选安全候选地图
无合适地图              → 回城安全待机并提示用户
```

同一地图重复死亡时延长冷却或本次运行跳过。不得自动复活、购买或试探地图访问限制。

## 11. 背包与仓库

### 11.1 物品状态

```text
BOUND：明确绑定/不可交易特征
UNBOUND：明确未绑定/可交易特征或已验证规则
LOCKED：装备、上锁、任务、货币、限时或用户禁止类别
UNKNOWN：无法可靠判断
```

`UNKNOWN` 永不移动；“没看到绑定”不代表 `UNBOUND`。

### 11.2 存仓规则

```text
进入已验证背包页
→ 按可见格子节流扫描
→ 筛选 UNBOUND + 用户白名单 + 非 LOCKED
→ 首次使用规则显示候选摘要供用户确认
→ 进入已验证仓库页
→ 一件一件存入
→ 验证背包数量减少且仓库数量增加/成功提示
→ 任一步失败立即停止
```

仓库满、密码、跨角色仓库、二次确认、未知弹窗进入人工接管。默认不自动出售、交易、邮寄、强化、合成、分解或丢弃。

## 12. 外部事件与恢复

### 12.1 分类

```text
STALLED：新帧存在但预期变化未出现
FRAME_STALLED：frame_seq 长时间不前进
GAME_CRASHED：游戏进程/前台消失
NETWORK_DEGRADED：加载或动作无回执
NETWORK_DISCONNECTED：明确断线/重连页
MAINTENANCE：维护、停服、活动关闭
PUSH_OCCLUDED：系统推送或遮挡
AUTH_REQUIRED：登录、验证码、实名认证、支付、权限
FRONT_APP_CHANGED：前台切换
LAN_IP_CONFLICT_SUSPECTED：网络地址冲突证据
UNKNOWN_EVENT：无法可靠分类
```

分类必须由一个明确错误页面或两个独立信号支持；单次 OCR 误读不得触发重启或重新登录。

### 12.2 无进展恢复

每个状态声明等待窗口、无进展阈值、安全重试数与允许恢复动作。统一阶梯：

```text
停止连续点击
→ 重新读取一帧并识别
→ 已知 loading：安静等待至窗口结束
→ 仅对幂等动作重试一次
→ 仅执行该状态白名单恢复动作一次
→ 仍失败：PAUSED_NEEDS_HELP
```

禁止把返回、关弹窗、重启游戏、连点屏幕作为通用自救。

### 12.3 闪退、网络与维护

```text
游戏闪退：释放会话 → 检查系统 PID/FC_N → 随机退避 10–30 分钟
          → 最多正常重开一次 → 未回到安全入口则暂停

网络延迟/掉线：停止新动作 → 随机退避 10–30 分钟 → 低频观察
              → 已学习重连按钮最多一次 → 重新验证资源和页面

维护/活动关闭：记录状态与可见结束时间 → 安排低频检查 → 不反复登录
```

退避时间由用户配置；重启后恢复同一计划，避免每次启动立即重连。

### 12.4 推送、账号与敏感页面

普通且已学习的无敏感遮挡可关闭一次并验证。账号、验证码、支付、权限、未知弹窗一律停止触控，显示人工接管。Agent 不代注册、不收取验证码、不填写密码。

### 12.5 IP 冲突

疑似冲突时只读记录接口地址、网关、DHCP 租约、默认路由、局域网可达性与游戏提示。不得强改静态 IP、伪造 MAC、修改路由器、杀网络进程、频繁开关 Wi‑Fi。若用户显式允许且系统支持，最多请求一次正常 DHCP 续租；仍异常则暂停并提示检查路由器 DHCP/静态租约。

### 12.6 清理与现场包

恢复或停止前只清理 ZiYan 自有资源：FrameLease、keep、触控会话、计时器、OCR/找图缓冲、临时请求回执和超限日志。不得清系统网络缓存、DNS、代理或系统服务。

现场包采用写盘节流，仅包含：最后关键帧索引、前一关键帧索引、状态、最近 20 条事件、front_bid、frame_seq、耗时、PID 摘要、恢复阶段和规则版本。

## 13. 局域网同步与多设备协作

### 13.1 同步对象

允许同步：

```text
已验证 GameProfile / ActivityProfile
state_graph、Lua 安全模板模块
版本、hash、bundle_id、游戏版本特征、验证证据
设备无关规则与本机 overlay 的独立摘要
```

禁止同步：

```text
密码、验证码、手机号、联系人、授权凭据、支付资料
远程触控命令、未审计任意脚本、二进制文件
逐帧截图、私聊原文或敏感现场
```

### 13.2 协议

采用“通知 + 拉取 + staging + 校验 + 原子启用”：

```text
设备 A 通过验证
→ 发布 manifest（规则版本、hash、适用 bundle、兼容标签）
→ 设备 B 收到通知并拉取至 staging
→ 校验设备信任、hash、路径、动作合同和游戏版本特征
→ B 在自身屏幕演练/校正
→ 成功后启用；失败则保留旧版本
```

爱快软路由只提供网络连通、发现或可选中转，不执行 Agent、不保存账号秘密。同步服务按需启动、空闲退出，不进入自动运行热路径。

### 13.3 双向自我校正

设备之间共享的是语义与验证证据，不是像素坐标：

```text
设备 A 成功 → 更新 A overlay + 共享候选规则
设备 B 拉取 → 重新在 B 上定位与验证 → 更新 B overlay
两端成功证据 → 提升共享规则 confidence
失败阈值达到 → 降级并回滚共享规则
```

单次成功不能覆盖全局；冲突保留双方版本，按游戏版本、成功率、最近验证和设备独立性选择候选，无法判断时人工确认。

## 14. 聊天、社团与账号安全边界

Agent 可在游戏规则允许时，对当前可见公屏做短期、可关闭的本地意图分类，例如：

```text
昵称：大哥大
意图：可能求购材料 / 寻找商人
置信度：0.91
```

不保存完整聊天原文，不提取联系方式，不跨游戏建立玩家画像，不自动私聊、加好友、群发或营销。游戏昵称仅可作为当前会话短期显示字段，并允许用户删除。

公会、行会、军团可以识别公开候选及用户指定条件，但每次申请或加入必须由用户确认；不得批量申请、自动接受陌生邀请或循环切换社团。

账号安全仅做提醒：封禁警告、异常登录、验证码、频率限制、维护、异常退出。不得分析或规避封号机制、轮换账号/设备规避风控。

## 15. 用户可见错误与暂停体验

任意 Lua、Python、人工学习生成脚本、Agent 会话都使用统一错误对象：

```text
script/profile、language、phase、error_code、message、line
session_id、detail_path、screenshot_index、rule_version
```

界面必须显示：

```text
名称：<脚本或活动>
阶段：load/runtime/main/vision/action/verify/recovery/timeout/stop
原因：简短可读说明
位置：行号或状态名（可获取时）
操作：[查看详情] [继续观察] [人工学习] [停止并清理] [回滚规则]
```

用户主动停止不是错误；停止后应明确显示资源已清理。

## 16. 性能与资源预算

### 16.1 资源纪律

1. 只在新帧到来后执行视觉判断；
2. 找色优先、找图按需、OCR 最少化；
3. 模板缓存有数量和字节上限，使用 LRU；
4. 不逐帧落盘，不无界保存截图、事件或聊天数据；
5. 高层规划低频触发，避免每帧重算；
6. 所有会话都有最大时长、动作数、重试数、日志大小和临时文件预算；
7. 超预算先降级 OCR/找图频率，再暂停；
8. 健康心跳只检查 frame_seq、front_bid、FC_N、会话和取消令牌，不建立第二守护进程。

### 16.2 运行后清理

任何停止、超时、崩溃、前台变化或异常恢复都必须释放：

```text
keep / FrameLease / 触控会话 / Lua/Python 句柄 / 定时器
模板临时引用 / OCR 中间图 / 学习缓冲 / 临时文件
```

## 17. 文件、路径与命名

用户可见逻辑根目录：

```text
/var/mobile/Media/ZiYan/
```

实际解析：

```text
rootful：/private/var/mobile/Media/ZiYan/
rootless：/var/jb/var/mobile/Media/ZiYan/
```

所有运行时代码必须走现有路径解析，不得写死单一路径。

游戏脚本命名为首字母大写拼音，冲突加序号：

```text
王者荣耀 → WangZheRongYao.lua
同名        → WangZheRongYao_2.lua
```

同名 JSON 元数据至少包含：

```text
display_name、pinyin_name、bundle_id、script_type、environment
profile_version、hash、created_at、source_device、verification_status
```

## 18. 测试与发布门禁

### 18.1 分层测试

```text
L0 静态：schema、路径、Lua 语法、动作合同、敏感规则
L1 离线：关键帧回放、状态识别、故障注入
L2 演练：真机不触控识别
L3 最小回放：单活动、低风险、单设备
L4 灰度：多次成功、单设备长期观察
L5 跨设备：rootful/rootless、不同屏幕的 overlay 验证
```

故障注入至少覆盖：按钮无效、坐标偏移、OCR 错误、未知页面、背包满、资源不足、被击杀、闪退、掉线、维护、推送遮挡、IP 冲突、前台切换和用户停止。

### 18.2 发布门禁

一个规则只有同时满足以下条件才能发布为自动运行：

1. 已学习且通过质量门槛；
2. DRY_RUN 通过；
3. 低风险真机回放通过；
4. 无未声明高风险动作；
5. 停止、异常、前台切换和资源释放测试通过；
6. 规则与设备 overlay 均可回滚；
7. 不破坏 `FC_N=1`、既有 find/touch 热路径和核心稳定性门禁。

### 18.3 决策质量指标

新策略不以点击次数衡量，而以：

```text
目标完成率、误动作率、无效重试率、资源浪费率
未知状态安全暂停率、恢复成功率、回滚率
平均 CPU/RSS、帧稳定性、长跑稳定性
```

任何指标明显退化，规则自动停止推广并回滚。

## 19. 实施顺序

### P0：不接入核心热路径的基础

```text

会话、规则、overlay、事件日志 schema
音量键互斥与停止清理
DRY_RUN 与现场查看
```

### P1：人工学习 MVP

```text
前后台识别
动作/前后帧记录
草稿状态图
质量报告

```

### P2：单游戏最小闭环

```text
已知游戏：打开 → 找到开始按钮 → 点击一次 → 验证成功
人工学习 → 演练 → 单机回放 → 回滚
```

### P3：活动与异常

```text
日常/Boss 活动卡片
无进展、死亡换图、闪退、掉线、维护、遮挡

```

每阶段都必须独立验收。禁止为了“看起来智能”跳过 P0–P2，先做大模型、联网服务或复杂战斗策略。

## 20. Cursor 执行约束

Cursor 实施 Agent 时必须：

1. 先读本文、`ROADMAP.md`、`今日项目进度.txt`、`.cursorrules` 和相关模块源码；
2. 一次只实现一个可验证主题；
3. 先建 schema/离线测试，再接真机；
4. 不修改 Desktop `ios7.lua` / `ios8p.lua`；
5. 不影响 `.53/.101/.112/.166` 的核心验收，也不在 `.149/.171` 部署 ZiYan；
6. 不得用重启 SpringBoard/backboardd、清系统网络或新增竞争守护来掩盖问题；
7. 每一刀输出假设、改动文件、回滚点、最小测试、设备证据和结论；
8. 未通过门禁不得宣称“通用自动玩游戏”“完全兼容”或“全面超越”。

## 21. 最终完成定义

Agent 功能完成不等于“能够盲目玩所有游戏”。完成必须同时满足：

```text
人工学习、演练、自动运行形成闭环
音量“-”与“+”分工正确且互斥
已学习单游戏流程可稳定回放
跨屏幕设备能独立校正，不套用绝对坐标
未知、异常、账号、敏感和高风险状态安全暂停
停止后无 keep、触控、会话、临时资源残留
规则有版本、证据、灰度与回滚
局域网同步不传隐私、不远程控制、不破坏本机核心
CPU/RSS、FC_N、前台跟帧和核心稳定性不退化
```

在这些条件完成前，不得把 Agent 描述为已具备通用自主游戏能力。

## 22. 受控自我迭代

Agent 的“自我迭代”是基于验证证据的规则改进，不是运行时任意改代码、自动扩大点击范围或绕过既有安全门禁。

### 22.1 允许迭代的内容

每次运行结束后，Agent 只可根据事件日志、成功率、耗时、失败原因和用户人工学习补充，生成候选改进：

```text
调整已学习活动的排序权重
调整已验证等待窗口和冷却时间
为新出现但已人工确认的状态补充视觉锚点
为设备自身更新 DeviceOverlay
将稳定成功路径提炼为新的 Lua 草稿版本
将持续失败规则降级、停用或回滚
```

候选改进必须先进入 `staging`，按“静态检查 → DRY_RUN → 单机低风险回放 → 灰度”通过后才可启用。任何单次失败、单次成功或未验证 OCR 结果都不得直接改写正式规则。

### 22.2 严禁自我修改的范围

Agent 不得自行修改：

```text
音量键停止逻辑、业务脚本互斥、FC_N=1、framecap 生命周期
SpringBoard/backboardd 相关代码、网络/系统设置、权限或账号逻辑
用户风险预算、敏感操作确认规则、隐私规则
Desktop ios7.lua / ios8p.lua、用户手写业务脚本、历史证据与回滚版本
```

需要改变这些内容时，必须由项目开发流程和用户明确决定，不能由学习数据自动驱动。

### 22.3 自我迭代质量门禁

每个候选规则都记录：来源会话、旧版本、新版本、差异、成功/失败样本、适用游戏版本、设备范围和回滚点。只有目标完成率不下降、误动作率/资源浪费率不增加、CPU/RSS/FC_N 不退化时才允许推广；否则自动停用候选并保留诊断。

## 23. 受控文件、日志与缓存清理

清理目标是限制 ZiYan 自己的磁盘、缓存和日志增长，不是“定期删除手机文件”。清理服务必须按需执行、空闲退出，不新增竞争守护进程，不进入视觉/触控热路径。

### 23.1 可清理范围

只允许清理由 ZiYan 生成、且在 manifest/索引中明确标记为可回收的文件：

```text
已完成会话的临时请求、回执和锁文件
过期 OCR 中间图、缩略图、模板临时副本
已上传/已归档的事件日志分片
DRY_RUN 与失败会话的低价值缓存
已被新版本替代且超过保留期的 staging 草稿
```

清理必须使用现有 rootful/rootless 路径解析，并且只在 ZiYan 自有目录内操作。

### 23.2 永不自动删除

```text
用户导入或手写的 Lua/Python 脚本
当前启用规则、最近一个稳定回滚版本、当前 DeviceOverlay
tmp_shots、VERDICT、崩溃诊断、人工标记为保留的现场
账号、系统、其他 App、Media 根目录外的文件
无法由 manifest 确认归属或仍被会话引用的文件
```

### 23.3 清理策略

```text
运行前：只清理上次异常遗留且未被引用的临时文件
运行后：释放本会话缓存和短期锁，不删除证据
空闲期：按大小上限和保留期候选清理
清理前：核对 manifest、引用计数、最后访问时间和当前会话
清理时：先移动到 ZiYan 回收区，延迟删除；失败可恢复
清理后：写入清理清单、释放字节数、保留原因和错误
```

禁止使用宽泛递归删除、未解析的通配符、系统目录清理或“清空全部缓存”策略。空间不足但没有安全候选时，应提示用户，而不是扩大删除范围。

### 23.4 日志与缓存预算

每类文件设独立预算和轮转策略：事件日志按大小/时间滚动；关键故障现场保留有限数量；OCR/模板缓存采用 LRU；staging 草稿按版本和保留期回收。达到预算先压缩/轮转低价值日志，再回收已确认缓存，最后暂停产生新大文件的学习会话。

## 24. 生成业务脚本的 ZiYan 自身函数约束

所有由 Agent 生成的 Lua 业务脚本必须仅调用 ZiYan 项目提供、已验证的函数与安全模板，不能依赖触动二进制、第三方常驻服务、任意 shell、私有网络服务或临时脚本拼接。

### 24.1 允许的生成结构

```text
ZiYan 路径解析
→ 已封装的找色/找图/OCR（按需）
→ 已封装的触控、等待、前台校验、停止检查
→ 状态机、动作合同、验证、超时与有限重试
→ ZiYan 统一日志和错误对象
```

生成脚本必须：

1. 使用已有 ZiYan Lua 模块和公开 API；
2. 在每个循环检查停止令牌、前台 Bundle 和超时；
3. 使用状态/锚点/相对区域，不写死某台设备绝对像素；
4. 不直接写 SpringBoard/系统控制文件，不执行 `os.execute`、任意 `io.popen` 或下载/执行外部代码；
5. 不写入用户脚本目录以外的任意路径；
6. 在生成后通过 Lua 语法、路径、动作白名单、敏感操作和资源预算检查。

### 24.2 生成失败与降级

如果所需能力没有 ZiYan 自身函数，生成器必须输出“缺少已验证能力”的结构化提示和人工学习草稿，而不是调用未验证外部模块。需要新增函数时，先由项目代码实现、单元测试、rootful/rootless 真机验证并纳入 ZiYan API，再允许生成器使用。

## 25. 函数能力缺失与 CPU/RSS 异常处理

Agent 生成和运行脚本前，必须查询 ZiYan 的函数能力注册表，而不是假设某函数存在、可用且性能稳定。每个函数至少登记：名称、参数契约、rootful/rootless 支持、同步/异步属性、资源成本等级、已验证版本、已知限制和替代函数。

### 25.1 函数能力不足

如果目标流程需要的函数不存在、不支持当前环境、参数契约不完整或尚未通过真机验证：

```text
CAPABILITY_MISSING
→ 停止生成可执行自动脚本
→ 输出缺失函数、需要的输入/输出、使用场景、目标环境和最小复现
→ 生成仅用于人工学习的草稿，不调用外部模块补洞
→ 将需求加入 ZiYan API 待实现队列
→ 新函数经过实现、静态测试、rootful/rootless 真机验证后才登记为可用
```

允许的降级只能使用已验证的 ZiYan 自身函数。例如 OCR 不可用时可降级为已学习的找色/找图条件；如果没有可靠替代，必须暂停，不得伪造识别结果或调用未审计外部服务。

### 25.2 函数性能看门狗

每次函数调用记录轻量指标：调用次数、耗时、超时、错误码、输入尺寸、临时内存估计、FrameLease/keep 状态和是否造成 `FC_N` 异常。监测必须复用现有会话和日志，不新增常驻性能守护。

出现以下任一情况时进入 `FUNCTION_DEGRADED`：

```text
连续超时或错误达到阈值
同一函数的耗时明显高于该设备基线
调用后 CPU/RSS 持续异常上升
临时图像、模板、keep、触控或文件句柄未释放
影响 frame_seq、前台跟帧、FC_N=1 或 SpringBoard/backboardd 稳定性
```

### 25.3 降级与隔离流程

```text
FUNCTION_DEGRADED
→ 立即停止该函数的新调用
→ 释放其临时图像、模板、lease、定时器和请求文件
→ 记录函数版本、设备、输入摘要、CPU/RSS/耗时证据
→ 尝试一个已验证、低成本替代函数
→ 无替代：PAUSED_NEEDS_HELP
→ 将该函数版本标记为本机 quarantine，不再被生成器选用
→ 修复并通过门禁后才解除 quarantine
```

不得通过降低等待时间、扩大循环频率、重启 SpringBoard/backboardd、清系统缓存或新增常驻进程来掩盖函数问题。

### 25.4 函数升级门禁

新增或修复函数必须按以下顺序：

```text
明确 API 契约与失败语义
→ 单元/离线测试
→ 单机 rootful 与 rootless 最小真机测试
→ CPU/RSS/资源释放检查
→ 与现有 find/touch/framecap 门禁无回归
→ 登记能力注册表
→ 生成器允许在 staging 中使用
```

函数未通过以上门禁时，不能被 Agent 自动选中，也不能被宣传为可用能力。

## 26. 自动反馈到项目的故障报告闭环

函数缺失、函数性能异常、规则失效、跨屏校正失败和异常恢复失败，都必须形成可被项目开发直接消费的结构化反馈，而不是只留下用户看不懂的 toast。

### 26.1 手机端报告生成

以下情况都自动创建同一种脱敏问题报告：

```text
Agent：CAPABILITY_MISSING、FUNCTION_DEGRADED、PROFILE_OUTDATED、
       CALIBRATION_FAILED、连续恢复失败、资源泄漏或异常停止
人工运行 Lua：加载/语法/运行/main/bridge/超时/embed 崩溃
人工运行 Python：加载/语法/运行/bridge/超时/无回执/子进程异常
```

用户主动按停止不是错误，不生成问题报告；只写普通会话结束记录。

每份报告包含：

```text
issue_id：时间 + 设备匿名 ID + 问题指纹
severity：P0 安全/系统稳定；P1 主流程阻断；P2 有替代方案；P3 体验问题
category：capability / cpu_rss / leak / vision / touch / network / profile / sync
function_or_rule：函数名、规则 ID、版本和 hash
script：业务脚本显示名、Lua/Python 类型、脚本 hash、可获取的行号（不复制脚本全文）
environment：rootful/rootless、iOS、设备型号、屏幕 profile
symptom：用户可读摘要与机器错误码
repro：最小复现步骤、输入摘要、前台 Bundle、frame_seq
metrics：耗时、调用次数、CPU/RSS 摘要、FC_N、keep/lease 状态
evidence：关键帧索引、最近事件、日志索引、回滚版本
recommended_action：停用/降级/补函数/重新学习/人工确认
```

报告不得包含密码、验证码、手机号、联系方式、私聊原文、完整敏感截图或其他账号秘密。

### 26.2 去重与升级

每个报告计算问题指纹：`函数/规则 + 错误码 + 环境 + 核心堆栈或状态`。同一问题短时间重复出现时只累加计数和最近证据，不无限生成文件。

```text
首次出现：创建 issue，标记 NEW
同指纹再次出现：更新 occurrences、last_seen、最近指标
跨两台设备复现：提升严重度并标记 CROSS_DEVICE
影响 FC_N/SB/BB/持续 RSS 上升：直接 P0，停止相关函数路径
```

### 26.3 项目接收路径

手机端统一逻辑目录：

```text
/var/mobile/Media/ZiYan/问题报告/待处理/<问题编号>/
```

实际路径：

```text
rootful：/private/var/mobile/Media/ZiYan/问题报告/待处理/<问题编号>/
rootless：/var/jb/var/mobile/Media/ZiYan/问题报告/待处理/<问题编号>/
```

问题编号使用中文来源前缀，例如：

```text
业务脚本_Lua_运行异常_20260815_183501
业务脚本_Python_超时_20260815_183501
智能体_找图函数性能异常_20260815_183501
```

每个问题报告至少包含：

```text
issue.json
summary.txt
events.jsonl（有限最近事件）
evidence_manifest.json
脚本错误摘要.txt（仅业务脚本错误时）
可选脱敏关键帧索引或缩略图
```

局域网可用时，SyncManager 仅同步已封包的 Issue Bundle 到项目接收区；网络不可用时本机排队，恢复后按 hash 去重上传。同步失败不得影响本机停止、降级或继续使用稳定规则。

### 26.4 项目侧处理契约

项目接收 Issue Bundle 后，Cursor/开发流程必须：

```text
读取 issue.json 与 evidence_manifest
→ 复现最小问题，不先改无关模块
→ 分类为函数缺失、性能回归、资源泄漏、规则过期或设备差异
→ 建立一个唯一修复主题与回滚点
→ 先离线/单机验证，再 rootful/rootless 真机验证
→ 回写修复版本、验收证据和关闭原因
→ 手机端收到新稳定版本后在 staging 演练，不直接覆盖运行会话
```

每个问题最终状态：`NEW`、`ACKNOWLEDGED`、`REPRODUCED`、`FIXED_IN_STAGING`、`VERIFIED`、`WONT_FIX` 或 `DUPLICATE`。用户在 Agent 页面可以看到简短状态，例如“找图函数在 iPhone 7 rootful 已被隔离，等待修复包”。

### 26.5 用户反馈入口

在错误/暂停页面提供：

```text
[查看问题摘要] [导出报告] [局域网同步报告] [继续使用稳定版本] [停止并清理]
```

用户可以额外勾选“附带当前画面”，默认只上传脱敏缩略图和索引；任何敏感页面该选项强制关闭。这样用户无需懂日志，也能把可复现的问题完整反馈到项目。

### 26.6 项目端接收目录与 AI 读取顺序

从手机导出的完整 Issue Bundle 统一复制到项目：

```text
/Users/mac/Desktop/ZiYan_副本/tmp_shots/智能体问题报告/待处理/<问题编号>/
```

目录内保持手机原始文件名，至少包含：

```text
issue.json
summary.txt
events.jsonl
evidence_manifest.json
```

禁止把原始报告复制到 `lua/`、`objc/`、`layout/`、项目根目录或直接覆盖 `DOCS/CURRENT_ISSUES.md`。`tmp_shots/智能体问题报告/待处理/` 是不可修改的原始证据区；修复后的结论另写入 `tmp_shots/智能体问题报告/已处理/<问题编号>/`，不覆盖原件。

项目侧维护一个轻量索引：

```text
/Users/mac/Desktop/ZiYan_副本/DOCS/智能体问题索引.md
```

索引只记录 `issue_id`、严重度、类别、函数/规则、设备范围、状态、原始证据路径、当前修复 commit 和最新 VERDICT 路径，不复制整份日志。

Cursor/AI 处理一条反馈时必须按顺序读取：

```text
.cursorrules
→ .cursor/skills/ziyan-verdict-loop/SKILL.md
→ ROADMAP.md
→ 今日项目进度.txt
→ DOCS/智能体问题索引.md
→ 对应 待处理/<问题编号>/issue.json
→ summary.txt
→ evidence_manifest.json
→ events.jsonl（只读相关时间窗口）
→ manifest 指向的最新 VERDICT/源码
```

只有在 `issue.json`、证据清单和复现条件齐全后，AI 才能提出修复；缺少文件时先标记 `INCOMPLETE_REPORT`，不得猜测性改代码。处理完成后在索引写回 `ACKNOWLEDGED/REPRODUCED/FIXED_IN_STAGING/VERIFIED` 等状态，并链接新的 VERDICT，不修改手机原始报告。

## 27. 最新 Agent 学习与自研工作流（2026-08-16 讨论版）

本章是对第 3、7、8、19、21 节中 **用户入口、人工学习与自动运行交互** 的最新覆盖说明。底层安全边界、动作合同、视觉优先级、性能纪律、错误报告和版本回滚规则仍以原章节为准。

本章只定义以下三项产品功能：

```text
学习用户游戏玩法
AI 自研游戏玩法
自动脱壳（入口独立保留；本章不定义其业务能力）
```

不再设置独立的“选择 Agent 游戏”正式按钮。选择目标游戏改为嵌入学习或自研流程，内部测试 Profile（观察回归、安全动作、AgentSmoke）不得出现在普通用户界面。

### 27.1 页面与状态显示

Agent 游戏页固定显示：

```text
当前学习/运行游戏：未选择 或 <游戏显示名>
标识：<bundle_id>
当前状态：未运行 / 等待锁定游戏 / 学习中 / 生成中 /
          自主探索中 / 迭代运行中 / 安全暂停 / 已完成 / 已取消

[学习用户游戏玩法]
[AI 自研游戏玩法]
[自动脱壳]
```

“我的脚本”只显示用户业务脚本列表；Agent 生成的 Lua 草稿作为普通脚本条目显示，但必须标识“学习草稿”或“自研草稿”和版本，不得伪装为稳定版本。

### 27.2 学习用户游戏玩法：一次确认开始、音量加结束

用户流程：

```text
点击“学习用户游戏玩法”
→ 前台弹出确认框：
  是否开始学习用户游戏玩法？
  开始后 ZiYan 将最小化，请在游戏内正常操作。
  [取消] [开始学习]

取消 → 状态=已取消；不最小化、不创建会话、不写目标。

开始学习
→ ZiYan 最小化
→ 状态=等待锁定游戏
→ 若已有合格游戏在前台，则锁定该游戏；否则等待用户自行打开首个合格第三方游戏
→ 状态=学习中
→ 用户正常操作游戏
→ Agent 被动记录用户动作与前后状态
→ 用户按音量“+”
→ 立即停止学习记录，进入生成中
→ 生成学习制品与 Lua 草稿
→ 提示“学习完成”或“学习内容不足，已生成报告”
```

学习模式不再要求第一次音量“+”启动；音量“+”在学习中只负责停止。若仍在“等待锁定游戏”时按音量“+”，取消本次学习，避免在未锁定目标时采集。

### 27.3 学习记录、隐私与生成物

锁定目标 bundle 后，Agent 仅在该 App 前台时记录用户的被动操作。记录每个动作的：

```text
动作类型、时间、逻辑坐标、归一化坐标、方向、安全区
front_bid、frame_seq、动作前后关键视觉特征、等待时间
前置状态、后置状态、是否发生可验证变化、异常分支
```

切换到 SpringBoard、系统设置、聊天、账号、验证码、支付、权限或其它 App 时，立即停止记录并进入安全暂停；不得监控或保存游戏外用户操作。

结束学习后按真实阶段汇报进度：

```text
0%   结束学习会话
15%  整理用户操作
35%  提取前后状态
55%  生成动作与验证草稿
75%  生成 Lua 业务脚本草稿
90%  执行语法、路径和安全检查
100% 保存完成
```

默认输出 Lua。Python 仅在其运行契约、资源预算和 ZiYan 自身函数调用均已通过对应环境门禁时作为可选输出，不能替代 Lua 热路径。

示例制品：

```text
/private/var/mobile/Media/ZiYan/
  LongJieZhengBa_BaDaoChuanQi_学习草稿.lua
  LongJieZhengBa_BaDaoChuanQi_学习草稿.json

/private/var/mobile/Media/ZiYan/Agent游戏/
  学习数据/<session>.jsonl
  运行记录/<session>_学习报告.txt
  生成脚本/<session>_质量报告.json
```

若缺少稳定前后状态、有效动作或安全可验证条件，只生成学习报告和 Profile 草稿，不得虚报已生成可执行业务脚本。

### 27.4 AI 自研游戏玩法：无学习内容

AI 自研不要求用户先有学习内容、演练结果或现成脚本。用户流程：

```text
点击“AI 自研游戏玩法”
→ 显示真实已安装 App 列表（排除 ZiYan 与内部测试 Profile）
→ 选择游戏
→ 弹出“确认当前目标”：
  当前选中：<显示名>
  标识：<bundle_id>
  [取消] [确认]
→ 确认后保存目标并打开目标游戏
→ 等待目标游戏成为前台
→ 状态=自主探索中
→ 按观察→识别→规划→动作→验证→恢复循环进行本地自研
→ 用户按音量“+”停止
→ 保存探索会话，进入生成中
→ 生成自研 Profile、状态图、Lua 草稿、迭代报告
→ 提示“已生成业务脚本”
```

“无需先有学习内容”不等于取消系统运行时保护。Agent 仍必须确认目标前台、帧源可用、取消令牌有效，并对敏感页面、未知高风险操作、无进展和资源异常执行安全暂停。该保护不要求用户额外操作，也不能被自研模式绕过。

首次自研生成示例：

```text
<游戏拼音>_自研草稿_v1.lua
<游戏拼音>_自研草稿_v1.json
```

### 27.5 AI 自研游戏玩法：已有学习或自研内容

当目标游戏存在学习草稿、自研草稿或稳定版本时：

```text
点击“AI 自研游戏玩法”
→ 显示：
  已发现 <游戏名> 学习内容
  当前版本：vX
  状态：学习草稿 / 自研草稿 / 稳定版本
  [取消] [继续迭代]
→ 继续迭代
→ 打开目标游戏
→ 调用当前版本业务脚本
→ Agent 观察执行步骤、状态变化、无进展、失败和设备校正偏差
→ 用户按音量“+”停止
→ 生成新版本草稿与迭代报告
→ 提示“已迭代业务脚本”
```

迭代只能以“旧版本保留 + 新版本生成”的方式进行：

```text
v1.lua 运行与保留
→ Agent 生成 v2.lua
→ 记录版本差异、来源会话、成功/失败、设备与规则 hash
→ 不覆盖 v1.lua
```

用户手写 Lua/Python 永不覆盖；运行中的脚本永不原地修改。新版本失败时保留旧版本与诊断证据。

### 27.6 自研决策循环与停止语义

自研运行的唯一决策循环为：

```text
观察画面
→ 状态识别（找色优先、找图按需、OCR 最少）
→ 选择当前最低风险候选动作
→ 执行一个声明式白名单动作
→ 验证画面、资源、前台或状态变化
→ 成功则更新 belief_state；失败则有限恢复或安全暂停
```

禁止用无限点击、无验证重试、任意 shell、自修改代码、网络下载或第二守护进程代替该循环。

音量键固定为：

```text
音量“-”：仅业务 Lua/Python 脚本。
音量“+”：学习中 / 自主探索中 / 迭代运行中 → 立即停止当前 Agent；
           等待锁定游戏 → 取消当前学习；
           空闲 → 进入 Agent 默认入口。
```

停止优先于视觉、OCR、规划、脚本生成和同步；停止后必须释放触控会话、FrameLease、keep、计时器、临时文件和短期缓冲。

### 27.7 不可突破边界

无论人工学习还是 AI 自研，均不得：

```text
自动处理登录、账号、密码、验证码、支付、充值、交易
修改系统、网络、音量键、守护进程、SpringBoard/backboardd 或核心函数
覆盖用户手写 Lua/Python 或历史版本
记录游戏外用户行为、私聊原文、联系方式或敏感页面内容
运行外部下载代码、任意 shell、云端大模型、Ollama、MCP 或常驻第二守护
```

### 27.8 分阶段完成定义

本章功能必须按以下顺序实现并独立验收：

```text
P1 学习会话：确认→最小化→锁定游戏→被动动作/前后状态记录→音量+停止
P2 学习生成：真实进度、学习报告、Lua 草稿、元数据、我的脚本可见
P3 首次自研：App 选择确认→打开游戏→有限观察/动作/验证→v1 草稿
P4 迭代自研：识别已有版本→继续迭代→调用旧版→生成 vNext→保留旧版
P5 稳定性：rootful/rootless、跨设备 overlay、CPU/RSS、停止清理和异常报告
```

任一阶段尚未实现时，界面必须准确说明当前能力，不得把观察骨架称为“已实现自动玩游戏”。

## 28. 三大模型协作架构与 Cursor 实施契约（架构师覆盖章）

本章把项目中已有的 `A→Codegen→B→C` 生成链、Lua `AI` 模块、视觉/验证模块与第 27 章 Agent 工作流统一为一个可实施的架构。它不表示要在手机上常驻运行三个大模型，也不允许把云 API、Ollama、iOS-MCP 或第二守护进程接入游戏热路径。

### 28.1 三大模型的正式语义

项目中的“三大模型”统一命名为：

| 编号 | 正式名称 | 现有可复用基础 | 唯一职责 | 禁止职责 |
|---|---|---|---|---|
| A | 感知与状态模型（Perception） | framecap、findColor/findImage、OCR、`ZiYanLiveVisionLearn`、`screen_sync` | 将帧、用户动作、前台、方向、锚点转为带置信度的观察结果 | 直接决定高层目标、直接无限点击、生成任意脚本 |
| B | 规划与脚本模型（Planner/Generator） | `lua/modules/AI.lua`、`ZiYanScriptGenerator`、知识库、学习事件 | 将已验证观察和历史证据转为 Profile、候选状态图、Lua 草稿、迭代差异 | 直接写系统文件、覆盖用户脚本、在热路径反复生成 |
| C | 审核与验证模型（Critic/Verifier） | `verify.lua`、结果验证、几何 Critic、错误报告、性能门禁 | 审核 A/B 的证据、动作合同、安全性、运行结果、CPU/RSS 与版本差异 | 自己生成业务逻辑、伪造 PASS、绕过停止或敏感页保护 |

`Codegen` 是 B 的一个受控输出步骤，不是第四个模型。现有 `A→Codegen→B→C` 字样必须逐步规范为：

```text
A 感知 → B 规划/生成 → C 审核/验证
```

若旧代码或历史报告仍出现 A/B/C 英文字母，必须在元数据中同时写入上述中文语义，避免 Cursor 和用户把测试侧车、HF 权重、DefenseAI 与游戏 Agent 混为同一运行实体。

### 28.2 三大模型不是并行常驻进程

三者按事件协作，不能并行争抢屏幕、触控、framecap 或同一脚本输出：

```text
唯一 ziyan_framecap
→ A 在“新帧 / 用户动作 / 前台变化”时产生 ObservationPacket
→ B 仅在“学习结束 / 迭代停止 / 明确状态变化”时消费已冻结观察集
→ C 在“准备动作 / 动作完成 / 生成完成 / 异常发生”时给出 Verdict
→ SessionController 根据 Verdict 允许、拒绝、暂停或进入下一步
```

硬规则：

```text
同一会话只有一个 ActionExecutor；
只有 C=ALLOW 的动作才可由执行器发送；
音量+停止可打断 A/B/C 任意阶段；
运行中的 Lua 不允许被 B 原地改写；
A/B/C 都不得新增 framecap、守护或高频轮询。
```

### 28.3 统一数据包，不允许自由文本互相“聊天”

三大模型只能通过版本化、可校验的结构化制品交流。禁止用散乱 `.txt`、隐式全局变量或不受控提示词作为跨模块真值。

```text
ObservationPacket（A 输出）
  session_id、bundle_id、device_profile、frame_seq、timestamp
  anchors、features、ocr摘要、user_action、before_after、confidence、sensitive_flag

PlanCandidate（B 输出）
  profile_id、source_session、base_version、states、actions、pre/postcondition
  budgets、risk、unknowns、generated_lua_path、hash

VerdictPacket（C 输出）
  subject_hash、decision=ALLOW/REJECT/PAUSE/ROLLBACK
  reason、evidence_refs、quality_score、performance_summary、next_action
```

逻辑目录：

```text
Agent游戏/会话/<session_id>/观察.jsonl
Agent游戏/会话/<session_id>/计划候选.json
Agent游戏/会话/<session_id>/审核结论.json
Agent游戏/生成脚本/<game>/<version>/
```

所有写入必须原子完成并带 schema_version、hash、source_session、created_at。rootful/rootless 实际路径必须走现有路径解析；不得将运行时真值散落到 Media 根目录。

### 28.4 A 模型：感知与状态模型实施边界

A 必须复用现有 ZiYan 函数与唯一帧源：

```text
新帧到达
→ 找色优先
→ 必要时相对 ROI 找图
→ 必要时最小 OCR
→ 结合用户动作前后帧、前台、方向和锚点
→ 输出 ObservationPacket
```

要求：

1. 只在目标游戏 bundle 前台时记录学习动作；
2. 只在新帧或用户动作时计算，禁止定频扫描全屏；
3. 必须使用归一化坐标、锚点、ROI 与 DeviceOverlay，禁止把单机绝对坐标当通用规则；
4. OCR 原文、敏感页面和聊天内容不得直接进入 Profile；
5. 置信度不足时输出 UNKNOWN，不得猜测为可执行状态；
6. A 只产生观察，不触控、不生成 Lua、不修改版本。

### 28.5 B 模型：规划与脚本模型实施边界

B 的输入只能是 C 已接受的观察证据、现有稳定版本、用户明确的目标与本机 DeviceOverlay。B 分为两个低频子阶段：

```text
学习编译：学习会话结束 → 状态/动作草稿 → Lua 草稿
自研迭代：运行结束 → 结果差异 → vNext 候选 Lua/Profile
```

要求：

1. 生成器默认输出 Lua，且仅使用 ZiYan 已验证函数与安全模板；
2. 生成的每个动作必须有前置、后置、超时、最大重试、风险与幂等性；
3. 无法表达的能力必须输出 `CAPABILITY_MISSING`，不能伪造 Lua 或调用外部模块；
4. B 只能生成新版本，采用 copy-on-write，不能改写运行中版本、稳定版本或用户手写文件；
5. B 不在游戏每一帧运行；没有学习结束、停止或明确迭代事件时不得启动；
6. 无本地侧车/模型权重时使用确定性规则生成与现有知识库，不得阻塞手机热路径等待外部模型。

### 28.6 C 模型：审核与验证模型实施边界

C 是唯一可以批准动作和版本提升的模块。它必须复用 `verify.lua` 的“动作前指纹 → 动作 → 新帧 → 后置验证”原则，并扩展为：

```text
输入：ObservationPacket / PlanCandidate / RuntimeResult
→ 检查前台、敏感页、动作白名单、前后条件、置信度、预算、函数能力
→ 检查 CPU/RSS、FC_N、FrameLease、keep、触控句柄、日志预算
→ 输出 ALLOW / REJECT / PAUSE / ROLLBACK
```

规则：

1. C=REJECT 或 PAUSE 时，执行器不得点击；
2. C 不能因“想完成目标”放宽敏感页、停止、风险动作或资源门禁；
3. 生成脚本经过语法、路径、函数能力、动作合同与风险检查后，才可写入“我的脚本”；
4. 新版本必须先保留为草稿；C 只记录是否具备提升候选资格，不得覆盖旧版；
5. 函数耗时、错误、CPU/RSS、FC_N 或 SB/BB 异常时，C 产出 `FUNCTION_DEGRADED` / `PAUSED_SAFE` 并触发第 25、26 节的报告闭环。

### 28.7 会话协调器：唯一仲裁点

新增或重构的 `AgentSessionController` 是三大模型唯一协调器，不是第四个模型。它负责：

```text
状态迁移、取消令牌、目标 bundle 锁定、资源所有权
一次只执行一个动作、进度事件、版本提交、错误报告路由
```

它必须拒绝下列非法转换：

```text
无目标直接进入 LEARNING / AUTONOMOUS
PAUSED_SAFE 后继续触控
STOPPING 后继续生成新动作
同一 session 同时运行业务脚本与 Agent
未验证候选覆盖稳定版本
```

### 28.8 Cursor 的完整阅读顺序与工作方式

Cursor 每次 Agent 工作不得只读第 27 章。固定阅读顺序为：

```text
.cursorrules
→ .cursor/skills/ziyan-verdict-loop/SKILL.md
→ ROADMAP.md（项目完成门禁）
→ ARCHITECTURE.md（单 framecap、设备分工、运行模型）
→ 今日项目进度.txt（最新包和已验收状态）
→ 本文第 0、2、4、5、6、7、8、9、12、16、18、22、24、25、26、27、28 节
→ 当前阶段关联源码与最新 VERDICT
```

开始实现前，Cursor 必须先输出并保存：

```text
方案一致性矩阵：章节 → 已实现 / 骨架 / 未实现 / 冲突 / 本轮不处理
本轮唯一主题：只允许一个 P 阶段
接口清单：A/B/C 输入输出、所有者、路径、版本与回滚点
验收清单：离线、rootful、rootless、四机证据
```

不得因为 UI 已出现、session 文件已写、测试 Profile 已跑而把某个章节标为完成。

### 28.9 分阶段交付图

```text
Z0 核心稳定（既有四机门禁）
→ A0/B0/C0：数据包 schema + SessionController + 版本目录 + C 静态审核
→ P1：A 学习被动记录
→ P2：B 学习编译 + C 草稿审核 + 我的脚本可见
→ P3：A/B/C 首次自研闭环（有限动作、验证、v1）
→ P4：既有版本迭代（vNext、差异、回滚）
→ P5：异常恢复、能力隔离、错误报告、跨设备 DeviceOverlay
→ Z2：四机 10/30 分钟资源稳定
```

任何阶段失败，回到该阶段的最小证据与接口契约修复；不得跨阶段堆功能，也不得以重启系统、关闭注入或删证据替代修复。
