### B3. 用户脚本主体执行两遍

- **文件**：`lua/ziyan_run.lua:526`；配合 `Script/Template/*.lua`、`Script/Examples/daily_reward.lua`
- **证据**：
  ```
  lua/ziyan_run.lua:519   local ok, runErr = pcall(chunk)      -- 执行脚本
  lua/ziyan_run.lua:526   if type(main) == "function" then     -- 又调一次 main
  lua/ziyan_run.lua:527     local mok, merr = pcall(main)
  ```
  所有随包模板尾部都带裸 `main()` 调用：
  ```
  Script/Template/auto_click.lua     main()
  Script/Template/login.lua          main()
  Script/Template/loop_task.lua      main()
  Script/Template/find_color.lua     main()
  Script/Template/ocr.lua            main()
  Script/Template/state_machine.lua  main()
  Script/Examples/daily_reward.lua   main()
  ```
- **本地复现**（模拟 runner 尾部契约）：
  ```
  MAIN_RAN count=1
  --- chunk 执行完毕 ---
  MAIN_RAN count=2      ← 主体跑了第二遍
  ```
- **判定**：**成立**。`pcall(chunk)` 已经把 `main()` 跑完，随后 runner 再 `pcall(main)`。
- **影响**：任何**抄模板**写出的用户脚本，整个自动化主体在一次会话内执行两遍——
  重复点击、重复登录、重复领奖、重复启动 App。第二遍还会撞上已被第一遍改动的 UI 状态，
  所以失败表现为"偶发、不稳定"，极易被误判为设备或找色问题。
  这直接影响 STRUCTURE.md 的铁律（业务效率 + 稳定性对比触动）。
- **修复**：让 `main` 只有一个所有者。二选一：
  - runner 侧：在 `pcall(chunk)` 前装 wrapper 标记 `_G.__ZIYAN_MAIN_CALLED`，已调用则跳过；
  - 脚本侧：删掉全部模板的尾部 `main()`，契约归 runner 独有。
  **建议 runner 侧**，因为存量用户脚本已在设备上，改 runner 才能一次覆盖全部。

## 2. High

### H0. 像素格式全局默认 BGRA 但 UICreate/CARender 产出 RGBA → 找色/快照 R/B 反转

- **文件**：`objc/shared/ZiYanFrameCapture.m:380`（消费方 `:2417`、`:2513`）
- **证据（赋值集我全部 grep 过，共 4 个写入点）**：
  ```
  :380   static uint8_t sLastSurfPixFmt = ZiYanFramePixelFormatBGRA8888;   ← 默认 BGRA(=0)
  :578   = RGBA8888   (ZiYanCaptureCompressedIOMFBViaAccel)
  :677   = RGBA8888   (ZiYanCaptureViaCreateScreenIOSurface)
  :684   = RGBA8888   (同上)
  :1063  = RGBA8888   (ZiYanCaptureViaIOMobileFB)
  ```
  **`ZiYanCaptureViaUICreateInProcess`(`:1288`) 与 `ZiYanCaptureViaCARender`(`:1271`)
  都不写这个变量**，但两者都会把 `sLastSurfPixFmt` 传进写入：
  `:2306 provider=UICreate`、`:2322 provider=CARender` → `:2417` / `:2513`。
- **两种像素格式确实是 RGBA（我独立核过，不是采信）**：
  - UICreate：`:1378-1380` 用
    `CGBitmapContextCreate(..., kCGImageAlphaNoneSkipLast | kCGBitmapByteOrder32Big)`
    → 内存序为 **RGBA**。
  - CARender：`:1213-1215` **显式**做 R/B 交换
    `drow[x*4+0]=row[x*4+2]; drow[x*4+2]=row[x*4+0];` → 输出 **RGBA**。
  - 枚举：`BGRA8888 = 0`、`RGBA8888 = 1`（`ZiYanFrameShm.h:41-42`）。
- **可达路径**（`:2298-2299`）：
  ```objc
  BOOL uiFirst = [iomfbErr containsString:@"surf_nil"] || !rootless;
  ```
  rootless（`.53`）且 IOMFB 失败**不是** `surf_nil` 时，pass 0 先跑 **CARender**；
  若它是本进程首个成功采帧，就沿用了 `:380` 的陈旧 BGRA 默认值。
- **消费方确实按该字段换 R/B**（我核了两处）：
  - `ZiYanSnapshotHttp.m:243-252`：`fmt == BGRA8888` 时交换 R/B 再编码 PNG。
  - `ZiYanColorMatch.m:120-135`：`sZCMPixFmt == 0` 时 `b=pix[0]; r=pix[2]`；
    调用方 `main.m:4338`、`ZiYanLuaEmbed.m:863/1030`、`ZiYanSnapshotHttp.m:481`
    都把 header 的 `pixel_format` 喂进来。
- **影响**：`.53`（iOS 15.8.8 rootless，项目声明的兼容性验收设备）上，
  IOMFB 不可用时**每一帧都被贴错标签**：`/snapshot` 产出 R/B 反转的 PNG，
  找色每次查表 R/B 颠倒 → 系统性 miss 或误命中。
  这与用户长期反馈的"找色对不上/命中点偏"症状同类。
- **修复**：在像素**产生处**赋值，而不是在兄弟函数里：
  CARender 转换结束(`:1243-1245`)与 UICreate `return sUiRgba;`(`:1405`)前各置 RGBA8888；
  并把 `:380` 初值改成 RGBA8888，使任何未赋值路径都无法说谎。

### H0b. `ServeLoop` 无锁读 `sLastCapChain` → 复现已修过的 `objc_retain+16` 崩溃类

- **文件**：读 `tools/ziyan_framecap/main.m:4641`（同形 `:1746`）；写 `:2958`
- **证据**：
  - 写方在锁内：`HandleOnce`(`:3335-3339`) 先 `ZiYanCaptureDecisionLock()` 再进
    `HandleOnceUnlocked`，`:2958 sLastCapChain = [chain copy];`
    该锁是**递归锁**（`PTHREAD_MUTEX_RECURSIVE`，`:195-203`）。
  - 读方**完全无锁**：`:4641` 位于 `ServeLoop` 函数体内
    ```objc
    BOOL iomfbNilHeavy = heavy3x && sLastCapChain &&
                         [sLastCapChain containsString:@"iomfb_surf_nil"];
    ```
    `:1746`（`RequestSbRelay` 内）同形。
  - **两个线程确实不同**：`ServeLoop()` 在主线程（`:5101` 调用）；
    `HandleOnceUnlocked` 可被**独立 detach 线程**到达——
    `ZiYanColorOffloadMain`(`:388`，`:422 pthread_create`) → `:400 PollColorReq()`
    → `:4450` 取锁 → `PollColorReqUnlocked`(`:3635`) → `:3697 HandleOnce(...)`
    → `:3335` 再取锁（递归，允许）→ `HandleOnceUnlocked:2958` **替换**该 `NSString`。
  - 旧对象 release 后，读方对已释放对象做 `objc_retain`。
- **决定性佐证**：**该文件自己在 `:187-192` 就记录了这个崩溃**——
  > "C-65.11-84：ServeLoop、color-offload 与快照/请求边界都可能进入 HandleOnce。
  > `sCaptureInFlight` 只是一枚普通 BOOL……**这条竞态曾把 framecap 崩在

  即：作者修了**入口**，但漏了 `ServeLoop`/`RequestSbRelay` 这两处**读共享静态**的地方。
- **影响**：framecap 间歇性 SIGSEGV（`objc_retain+16`），主循环死掉 →
  脚本失去帧源、P4 门禁间歇性失败且**没有崩溃报告**。
  冷闲态（`cold_idle→shm_clear` 每 5s）使 `:3694` 的 `noPix` 前置条件真实成立，提高触发率。
- **修复**：读方也纳入 `ZiYanCaptureDecisionLock`（递归锁，嵌套安全），

### H1. 共享帧"跳过像素"闩锁会用新时间戳发布旧像素

- **文件**：`objc/shared/ZiYanFrameShm.m:422`（配合 `:426`、`:515`、`:21-31`）
- **机制**（我自己完整追了一遍几何判定，修正了初版结论）：
  ```c
  BOOL skipPx = embedHot && sFilePixelsSeeded;
  if (!skipPx) { memcpy(map + sizeof(hdr), pixels, payload); sFilePixelsSeeded = YES; }
  ...
  hdr->seq = next;  hdr->ts_ms = ts;  hdr->commit_seq = c0 + 1u;   // 无条件推进
  ```
- **精确定界**（重要，避免误报）：
  - 同几何分支要求 `st.st_size == total` **且** `width/height/bpr/payload` 与本次完全一致，
    所以 skip 分支的字节数必然相同——**不存在越界写**。
  - `ZiYanFrameShmClear()` 会把文件 rename 成 header-only，导致下一次写入 `st_size != total`
    而**强制走全量分支**，所以 Clear 之后不会复用旧像素。
  - `sFilePixelsSeeded` 是进程内 `static`，**不可能被跨进程装配**——初版报告的这一段不成立。
- **成立的部分**：在 `.ziyan_lua_embedded` 存在（embed 热路径）时，
  同一进程内第二次起的写入会**只更新 header、不更新像素**，但 `ts_ms`/`seq`/`commit_seq`
  全部推进。读**文件**像素的消费者拿到的是冻结帧，而所有新鲜度门禁（`IsFresh`/`PeekAgeMs`）都通过。
- **实证消费者**（都走 `ZiYanFrameShmMapRead`，不读 resident）：
  ```
  tools/ziyan_framecap/ZiYanSnapshotHttp.m:1081   → HTTP /snapshot
  tools/ziyan_framecap/main.m:793, 842, 3144
  objc/app/OverlayWindow.m:244
  objc/shared/ZiYanFrameTrace.m:124
  ```
- **影响**：embed 场景下这些消费者会**自信地报告错误结果**（旧画面），而不是报 stale 错误。
- **修复**：skip 必须可证明而非靠记忆——把"本 seq 像素已提交"作为显式入参，
  或在 `ZiYanFrameShmClear` 与几何/inode 变化时复位 `sFilePixelsSeeded = NO`。

## 3b. 第二轮补充发现（全部由我独立复现）

### N1. High — `waitUntil` 系列用 CPU 时间当墙钟预算，超支 30–100 倍

- **文件**：`lua/modules/Timer.lua:71-72`；同形存在于
  `Image.lua:88-89`、`OCR.lua:231-232`、`Script.lua:182-183`
- **证据**：`local t0 = os.clock()` + `while (os.clock()-t0)*1000 < timeout_ms do ... sleep_ms(interval_ms)`
- **我的实测**（复刻该循环形状）：
  ```
  预算 300ms -> 实际迭代 101 次
  os.clock 计得 CPU 时间 = 34.50 ms  (预算仍未耗尽: true)
  真实墙钟 ≈ 10100 ms  => 超支约 33.7x
  ```
  原因：`os.clock()` 是 **CPU 时间**，`sleep`/IPC 阻塞期间几乎不增长。
- **影响**：所有 `*Until`/`waitUntil` API 的 `timeout_ms` 形同虚设，
  在 24/7 长跑脚本里表现为**永不超时的挂起**，而不是按预算失败。
  `Chat.lua:20-21` 就在 `openFixture` 里调 `Timer.waitUntil(..., 8000, 250)`。
- **修复**：改用墙钟（`os.time()` 秒级对 ≥1s 调用者已够；有单调钟更好），四处一起改。

### N2. High — 音量回调在事件文件写满后**永久失效**

- **文件**：`lua/modules/Input.lua:179-186`（生产者 `objc/tweak/springboard/Tweak.m:285-298`）
- **机制**：Lua 用单调递增高水位 `VM._poll_pos` 比对
  `if #body <= VM._poll_pos then return false end`；而 ObjC 生产者**把文件截在 3000 字符**：
  ```objc
  if (body.length > 3000) { body = [body substringFromIndex:body.length - 3000]; }
  ```
  文件一旦到达 ~3000，`#body == _poll_pos` **永久成立**，
  之后每次音量键写入的 `event=VolumeDown` / `hook=decreaseVolume` 都读不到。
- **影响**：音量触发功能在累计足够音量活动后**静默死掉**，直到进程重启。
  一次性冒烟测试只 poll 一次，抓不到该形态。
- **修复**：消费式读取（读完 `os.remove` + 复位 `_poll_pos = 0`），
  或改成跟踪尾部增量而非绝对偏移。

### N3. High — 离线队列 wget 分支把未知 HTTP 状态当 200，**永久丢弃报告**

- **文件**：`lua/modules/OfflineQueue.lua:322-325`（判定在 `:343`，落盘在 `:364-375`）
- **证据**：curl 分支带 `-w '__HTTP__%{http_code}'`，**wget 分支没有对应标记**：
  ```lua
  local code = tonumber(output:match("__HTTP__(%d+)%s*$") or "200") or 200
  if code < 200 or code >= 300 then return false, "http_" .. tostring(code) end
  ```
  wget 路径下 match 为 nil → 默认 200 → 判定通过。
  随后 `st.status = "sent"`、`st.sent_at = os.time()` 被 `write_state` **持久化**，
  事件离开重试集，2c) 的 `/dev/tcp` 兜底也因 output 非空被跳过。
- **影响**：任何"有 wget 无 curl"的设备上，服务器 500/404 会被当成上传成功，
  **报告被永久丢弃**——恰好击穿"服务器故障时日志必须留存"的设计目标。
- **修复**：wget 分支也输出状态码；或标记 `code_known=false` 并返回
  `false, "http_status_unknown"`，绝不默认 200。

### N4. High — 回滚失败被上报为成功，随后把坏文件当新版本提交

- **文件**：`lua/modules/OptimizationRollback.lua:145-148`（消费方 `Optimization.lua:683-687`）

- **文件**：`lua/json.lua:253-261`（`parse_string` 内的三段 `gsub` 顺序）
- **证据**：顺序是 代理对 → `\uXXXX` → `"\\.", escape_char_map_inv`。
  最后一步的 `\\.` 会把上一步刚解出的**真实反斜杠**连同后一个字符一起吃掉。
- **我的实测**：
  ```
  输入 "\t\u005Cn"   实际 bytes = 09 0A        期望 = 09 5C 6E
  输入 "\u005Cz\n"   实际 bytes = 5C 7A 0A     期望 = 5C 7A 0A   （碰巧对）
  ```
  注意 `"\u005Cz"` 碰巧正确，所以缺陷很隐蔽。
- **严重度定级依据（我自己核过）**：初版子代理称"活跃暴露：CPython `ensure_ascii=True`
  遇非 ASCII 会产出 `\u005C`"。**实测不成立**：
  ```
  CPython: json.dumps("中文\\temp", ensure_ascii=True) -> "\u4e2d\u6587\\temp"   （用 \\，非 \u005C）
  扫描 U+0020–U+007E 全部字符，ensure_ascii 无一会产出 \u00XX
  JS:      JSON.stringify 同样只用 \\
  ```
  因此这是**潜伏缺陷**：本库自身 `encode`/`decode` 往返**自洽**
  （实测 `C:\Users\test`、`路径 C:\temp\日志`、`a\b\c` 三样本往返全一致），
  只有当第三方生产者**显式**发出 `\u005C` 时才触发。
- **修复**：把 `"\\.", escape_char_map_inv` 这一步**移到两个 `\u` pass 之前**，或合并为单趟扫描。
- **同源（未定级）**：`parse_unicode_escape`（`:207-216`）缺低代理区间校验。
  实测孤立高代理 `"A\ud800B"` → 原样透传 `41 5C 75 64 38 30 30 42`（未解码也未报错），
  `"\ud800\u0041"` → `E2 91 81`(U+2441，静默错字)；合法代理对 `\ud83d\ude00` → `F0 9F 98 80` 正确。
  建议加 `0xDC00 <= n2 <= 0xDFFF` 校验并对孤立代理报错。
